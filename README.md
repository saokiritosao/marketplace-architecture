# Marketplace API на Go

Это второе домашнее задание про OpenAPI, CRUD и бизнес-логику маркетплейса.
Проект сделан как одно Go-приложение с модулями для пользователей, товаров,
заказов и промокодов. Рядом поднимаются PostgreSQL и Flyway.

Я специально не разбивал эту работу на микросервисы. Создание заказа должно
одновременно уменьшить остатки, сохранить позиции, применить промокод и записать
операцию пользователя. В одном приложении и одной базе это можно сделать обычной
транзакцией PostgreSQL. Для учебной работы это проще и надёжнее, чем добавлять
саги и компенсации.

## Что есть в проекте

- OpenAPI 3.0.3 как основной контракт API;
- генерация Go-моделей и серверного интерфейса через `oapi-codegen`;
- CRUD для товаров;
- пагинация и фильтры;
- PostgreSQL и миграции Flyway;
- единый формат ошибок;
- валидация запроса по OpenAPI до вызова бизнес-логики;
- создание, изменение и отмена заказа в транзакции;
- блокировка товаров через `SELECT ... FOR UPDATE`;
- промокоды двух типов;
- JWT access/refresh token;
- роли `USER`, `SELLER`, `ADMIN`;
- JSON-логи каждого запроса;
- готовый демонстрационный скрипт и SQL-запросы для защиты.

## Быстрый запуск

Нужен установленный Docker с командой `docker compose`. Для готового demo-скрипта также нужны `curl` и `python3`.

При желании можно скопировать настройки окружения:

```bash
cp .env.example .env
```

```bash
docker compose up --build -d
```

Проверить контейнеры:

```bash
docker compose ps
```

PostgreSQL с компьютера доступен на `localhost:5433` по умолчанию. Сам API внутри Docker обращается к базе по имени сервиса `postgres`.

Проверить API:

```bash
curl -i http://localhost:8080/health
```

Ожидаемый ответ:

```text
HTTP/1.1 200 OK
```

```json
{"status":"ok"}
```

Посмотреть логи приложения:

```bash
docker compose logs -f api
```

## Готовая демонстрация

Скрипт регистрирует пользователей, создаёт товар и промокод, оформляет заказ,
изменяет и отменяет его, а затем показывает несколько ошибок и переходы статусов.

```bash
bash scripts/demo.sh
```

После этого показать таблицы PostgreSQL:

```bash
make db
```

То же самое без `make`:

```bash
docker compose exec -T postgres \
  psql -U marketplace -d marketplace -f /scripts/defense.sql
```

Остановить проект:

```bash
docker compose down
```

Полностью удалить локальную базу и начать заново:

```bash
bash scripts/reset.sh
```

## Кодогенерация

Главный контракт находится здесь:

```text
api/openapi/marketplace.yaml
```

Сгенерировать модели и серверный интерфейс:

```bash
make generate
```

Результат:

```text
internal/api/generated/marketplace.gen.go
```

Этот файл добавлен в `.gitignore`. Docker тоже запускает генерацию во время
сборки, поэтому проект не зависит от случайно сохранённой локальной версии файла.

Локальная сборка:

```bash
make build
```

Полная локальная проверка генерации, форматирования и тестов:

```bash
make verify
```

Только тесты:

```bash
make test
```

Для локальной сборки без Docker нужен Go 1.26 и работающий PostgreSQL.

## Основные endpoint'ы

| Метод | URL | Что делает |
|---|---|---|
| `POST` | `/auth/register` | регистрирует USER или SELLER |
| `POST` | `/auth/login` | возвращает access и refresh token |
| `POST` | `/auth/refresh` | обновляет пару токенов |
| `POST` | `/products` | создаёт товар |
| `GET` | `/products` | возвращает страницу товаров |
| `GET` | `/products/{id}` | возвращает один товар |
| `PUT` | `/products/{id}` | полностью обновляет товар |
| `DELETE` | `/products/{id}` | переводит товар в `ARCHIVED` |
| `POST` | `/orders` | создаёт заказ и резервирует остатки |
| `GET` | `/orders/{id}` | возвращает заказ |
| `PUT` | `/orders/{id}` | заменяет позиции заказа |
| `POST` | `/orders/{id}/cancel` | отменяет заказ и возвращает остатки |
| `PUT` | `/orders/{id}/status` | двигает заказ по цепочке статусов, только ADMIN |
| `POST` | `/promo-codes` | создаёт промокод |

## Как устроен код

```text
HTTP-запрос
    ↓
middleware
    ↓
handler
    ↓
service
    ↓
repository
    ↓
PostgreSQL
```

### `handler`

Файлы в `internal/httpapi` работают с HTTP: читают сгенерированный DTO, вызывают
сервис и формируют ответ. Сложной логики там нет.

### `service`

Файлы в `internal/service` содержат правила: кто может менять товар, можно ли
создать заказ, хватает ли остатка, действует ли промокод и разрешён ли переход
статуса.

### `store`

Файлы в `internal/store` содержат SQL. ORM здесь не используется, поэтому на
защите можно открыть запрос и сразу показать, что происходит с базой.

## Несколько важных решений

### Деньги не хранятся во `float64`

OpenAPI принимает число, но после входа оно переводится в целое количество
копеек. Например, `2499.90` превращается в `249990`. В PostgreSQL деньги лежат в
`NUMERIC(12,2)`. Так расчёты скидок не зависят от ошибок двоичной дроби.

### Цена копируется в заказ

В `products.price` находится текущая цена. В `order_items.price_at_order`
сохраняется цена на момент заказа. Если продавец поменяет цену завтра, старый
заказ не изменится.

### Остатки блокируются

Перед резервированием выполняется `SELECT ... FOR UPDATE`. Пока транзакция не
закончилась, другой заказ не может одновременно изменить те же строки товаров.
Это защищает от ситуации, когда два пользователя покупают последнюю единицу.

### Обновление заказа не оставляет половину изменений

При обновлении заказа старая бронь сначала возвращается только внутри текущей
транзакции. Затем проверяются новые позиции и создаётся новая бронь. Если на
любом шаге возникает ошибка, PostgreSQL откатывает всё целиком.

### Удаление товара мягкое

`DELETE /products/{id}` не удаляет строку. Он меняет статус на `ARCHIVED`. Это
оставляет историю и не ломает ссылки из старых заказов.

### JWT не создаёт серверную сессию

Каждый защищённый запрос приносит access token в заголовке `Authorization`.
Сервер проверяет подпись, срок и роль, а затем кладёт пользователя в context.
Refresh token используется только в `/auth/refresh`.

### Логи не сохраняют пароль

Для `POST`, `PUT`, `DELETE` логируется request body, но поля `password`,
`access_token` и `refresh_token` заменяются на `***`. Каждый ответ получает
заголовок `X-Request-Id`.

## Структура

```text
api/openapi/                 OpenAPI-контракт
cmd/api/                     запуск приложения
internal/httpapi/            HTTP-обработчики
internal/service/            бизнес-правила
internal/store/              SQL и транзакции
internal/middleware/         JWT, валидация, логи, recovery
internal/security/           создание и проверка JWT
migrations/                  миграции Flyway
scripts/demo.sh              E2E-сценарий
scripts/defense.sql          SELECT для защиты
docs/                        объяснения и шпаргалка
```
