# Пример текста для защиты

Ниже не текст для чтения слово в слово, а нормальная последовательность, по
которой удобно рассказывать и переключаться между файлами.

---

Я сделал API маркетплейса на Go. В этой работе основной подход contract-first:
сначала описан контракт в OpenAPI, а уже из него генерируются Go-модели и
интерфейс обработчиков.

Главный файл находится в `api/openapi/marketplace.yaml`. В нём описаны URL,
HTTP-методы, входные и выходные модели, коды ответов, ошибки, ограничения полей и
JWT-схема.

Код генерируется командой:

```bash
make generate
```

Она создаёт `internal/api/generated/marketplace.gen.go`. Этот файл не хранится в
Git, он генерируется заново во время сборки. В своих обработчиках я реализую
сгенерированный `ServerInterface` и использую сгенерированные модели. Отдельных
ручных HTTP DTO нет.

Само приложение сделано модульным монолитом. То есть это один процесс и одна
PostgreSQL, но код разделён на товары, заказы, пользователей и промокоды. Я не
стал делать несколько микросервисов, потому что создание заказа по условию
должно одним действием уменьшить остатки, создать заказ, применить промокод и
записать операцию. В одной базе это обычная транзакция. Между несколькими
сервисами пришлось бы делать сагу и компенсации, что для этого задания только
усложнило бы работу.

Путь запроса выглядит так:

```text
middleware → handler → service → store → PostgreSQL
```

Middleware проверяет JWT, валидирует запрос по OpenAPI и пишет JSON-лог.
Handler работает с HTTP. Service содержит правила. Store содержит SQL.

Например, `POST /products` сначала проверяется по OpenAPI. Если цена отрицательная
или имя слишком длинное, запрос до service вообще не доходит. Потом JWT
middleware получает ID и роль пользователя. Handler читает тело в
сгенерированный `ProductCreate`, а service проверяет роль. Товар может создать
SELLER или ADMIN. В store выполняется INSERT в PostgreSQL.

Для товаров реализованы создание, получение, список, обновление и мягкое
удаление. `DELETE` не удаляет строку, а меняет статус на `ARCHIVED`. На поле
`status` есть индекс. `created_at` заполняется default-значением, а `updated_at`
обновляется trigger'ом.

Самая большая часть работы находится в заказах.

При создании заказа сначала блокируется строка пользователя. Это нужно, чтобы
два параллельных запроса одного пользователя не прошли одновременно проверку
лимита и активного заказа. После этого товары выбираются через `FOR UPDATE`.
Пока транзакция не завершилась, другой заказ не сможет изменить эти же остатки.

Дальше проверяется, что все товары существуют, находятся в `ACTIVE` и остатка
хватает. Только после всех проверок stock уменьшается. Цена копируется в
`price_at_order`, потому что цена товара потом может измениться, а старый заказ
должен остаться прежним.

Если есть промокод, он тоже блокируется. Проверяется срок, активность, число
использований и минимальная сумма. После этого считается скидка и увеличивается
`current_uses`.

Все эти действия идут в одной транзакции. Если ошибка возникнет на любом шаге,
PostgreSQL откатит и заказ, и остатки, и промокод.

При обновлении заказа старая бронь сначала возвращается внутри той же
транзакции. Потом проверяется новый набор товаров и создаётся новая бронь. Если
нового остатка не хватает, вся транзакция откатывается, поэтому старый заказ не
ломается.

При отмене возвращаются остатки, уменьшается использование промокода и статус
становится `CANCELED`. Отмена вынесена в отдельный
`POST /orders/{id}/cancel`, потому что это не обычное редактирование одного поля,
а команда с несколькими последствиями.

Для проверки модели состояний есть административный
`PUT /orders/{id}/status`. Он разрешает только последовательные переходы:

```text
CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED
```

Если попробовать перейти сразу из `PAYMENT_PENDING` в `SHIPPED`, вернётся
`409 INVALID_STATE_TRANSITION`.

Для денег внутри Go используется целое число копеек. Я не считаю стоимость во
`float64`, потому что двоичные дроби могут давать неточное значение. В базе
деньги хранятся как `NUMERIC(12,2)`.

Авторизация сделана через JWT. Access token живёт 20 минут, refresh token — 14
дней. Сервер не хранит HTTP-сессию: каждый запрос сам приносит access token.
Роль находится в claim `role`.

Проверка роли есть в service, а не только в middleware. Middleware может узнать,
что пользователь SELLER, но только service после чтения товара понимает, его ли
это товар.

Каждый запрос попадает в JSON-лог. В нём есть request ID, метод, endpoint, код,
время работы и user ID. Для POST, PUT и DELETE пишется body, но пароль и токены
заменяются на `***`. Тот же request ID возвращается в `X-Request-Id`.

Теперь я покажу запуск.

```bash
docker compose up --build -d
docker compose ps
curl -i http://localhost:8080/health
```

Затем можно запустить готовый сценарий:

```bash
bash scripts/demo.sh
```

Он показывает успешные запросы и несколько ошибок: недостаток прав,
контрактную валидацию, лимит частоты и неправильный переход состояния.

После запросов я покажу данные напрямую в PostgreSQL:

```bash
make db
```

Там видны пользователи, товары, заказы, позиции, промокоды и операции
пользователя.
