# Вопросы, которые могут задать на защите

Ответы специально написаны обычным языком. Лучше понимать мысль, а не учить
каждую фразу.

## REST и HTTP

### Что такое REST?

REST — это архитектурный стиль для распределённых систем. Он задаёт несколько
ограничений: клиент и сервер разделены, запросы stateless, ресурсы имеют единый
интерфейс, ответы можно кэшировать, а система может состоять из нескольких
слоёв.

REST не говорит, на каком языке писать сервер. Чаще всего его реализуют поверх
HTTP и JSON.

### Почему REST — стиль, а не протокол?

Протокол точно задаёт формат сообщений и правила обмена. REST задаёт общие
принципы. Поэтому два REST API могут иметь разные JSON, разные URL и разные
ошибки. От разработчика всё равно зависит, насколько последовательно он
спроектирует контракт.

### Какие основные принципы REST?

Для защиты достаточно назвать:

- client-server;
- stateless;
- cacheable;
- uniform interface;
- layered system;
- code on demand как необязательное ограничение.

В моём проекте особенно видны stateless, ресурсные URL и единое использование
HTTP-методов и кодов.

### Что значит stateless?

Сервер не хранит между HTTP-запросами состояние пользовательской сессии. Каждый
защищённый запрос сам приносит access token и всю информацию, которая нужна для
проверки пользователя.

Это не значит, что сервер вообще ничего не хранит. Товары и заказы всё равно
лежат в PostgreSQL. Stateless относится именно к состоянию разговора клиента с
сервером между запросами.

### Почему stateless важен?

Запрос может обработать любой экземпляр приложения. Не нужно направлять одного
пользователя всё время на один сервер. Проще масштабировать API и восстанавливать
его после сбоя.

### Что такое ресурс в REST?

Ресурс — объект предметной области, с которым работает API. В этой работе это
товар, заказ, пользователь и промокод.

Поэтому URL выглядит как `/products/15`, а не `/getProduct?id=15`.

### Как правильно проектировать URL?

В URL обычно ставят существительные и коллекции:

```text
/products
/products/{id}
/orders/{id}
```

Действие задаётся HTTP-методом. Не стоит делать `/createProduct`,
`/deleteProduct`, `/getAllProducts`.

### Почему отмена заказа выглядит как `/orders/{id}/cancel`?

Отмена — не простая замена одного поля. Она возвращает остатки, уменьшает
использование промокода и меняет статус в одной транзакции. Поэтому это отдельная
бизнес-команда.

Можно спорить о форме URL, но такой вариант явно показывает смысл операции и
прямо требуется в задании.

### Какие HTTP-методы соответствуют CRUD?

```text
Create  → POST
Read    → GET
Update  → PUT или PATCH
Delete  → DELETE
```

В проекте обновление сделано через PUT, потому что клиент передаёт полное новое
состояние изменяемых полей товара или полный новый список позиций заказа.

### Чем PUT отличается от PATCH?

PUT обычно передаёт полное новое представление изменяемой части ресурса. PATCH
меняет только отдельные поля. В этом задании требуется PUT, поэтому, например,
`ProductUpdate` содержит все основные изменяемые поля.

### Что такое идемпотентность?

Повтор одинакового запроса оставляет систему в том же итоговом состоянии.

GET идемпотентен, потому что ничего не меняет. PUT обычно идемпотентен: повторная
установка одних и тех же данных даёт тот же результат. DELETE тоже считается
идемпотентным: после первого удаления ресурс уже удалён или архивирован.

POST обычно не идемпотентен. Два одинаковых `POST /products` могут создать два
товара.

### Почему идемпотентность важна?

Клиент может отправить запрос, не получить ответ из-за сети и повторить его.
Если операция не учитывает повтор, можно случайно создать два платежа или два
заказа.

В этой работе создание заказа защищено ограничением активного заказа и
транзакцией, но отдельный idempotency key не требуется заданием.

### Какие группы HTTP-кодов есть?

```text
1xx — информационные
2xx — успех
3xx — перенаправление
4xx — ошибка запроса или прав клиента
5xx — ошибка сервера
```

### Какие коды используются в проекте?

- `200 OK` — успешный GET или PUT;
- `201 Created` — ресурс создан;
- `204 No Content` — товар переведён в `ARCHIVED`;
- `400 Bad Request` — контрактная валидация;
- `401 Unauthorized` — токен отсутствует, неверный или истёк;
- `403 Forbidden` — пользователь известен, но прав нет;
- `404 Not Found` — товар или заказ не найден;
- `409 Conflict` — конфликт с текущим состоянием;
- `422 Unprocessable Entity` — промокод понятен, но применить его нельзя;
- `429 Too Many Requests` — операция выполняется слишком часто;
- `500 Internal Server Error` — неожиданная ошибка;
- `503 Service Unavailable` — health-check не может обратиться к БД.

### Почему недостаток остатка — 409, а не 400?

Сам JSON правильный. Проблема возникла из-за текущего состояния ресурса: товара
сейчас недостаточно. Поэтому это конфликт с состоянием системы.

### Почему промокод возвращает 422?

Запрос понятен и формат кода правильный, но именно этот промокод истёк, исчерпан
или не подходит по минимальной сумме. Сервер понимает запрос, но не может
применить его по бизнес-правилам.

### Почему нельзя всегда возвращать 200 и писать ошибку в body?

Клиенту пришлось бы разбирать тело каждого ответа, чтобы понять, был ли успех.
HTTP-код уже даёт стандартный сигнал для библиотек, мониторинга и прокси.

### Какие частые ошибки делают в REST API?

- глаголы в URL;
- один код `200` на всё;
- POST для любого действия;
- отсутствие пагинации;
- разные форматы ошибок;
- возврат структуры таблиц прямо наружу;
- отсутствие валидации и проверки прав;
- путаница между `401` и `403`;
- физическое удаление данных, которые нужны истории;
- игнорирование конкурентных запросов;
- отсутствие ограничений размера списка и страницы.

### Что такое HATEOAS?

Это подход, при котором ответ содержит ссылки на следующие доступные действия.
Например, заказ в `CREATED` мог бы содержать ссылку `cancel`, а завершённый заказ
её уже не содержал бы.

HATEOAS помогает клиенту узнавать допустимые переходы из ответа, а не хранить
всю навигацию отдельно. В этом задании он не требуется, поэтому я его не
добавлял.

### Что такое short polling?

Клиент раз в несколько секунд делает обычный запрос и спрашивает, изменилось ли
состояние. Например, `GET /orders/15` каждые пять секунд.

Это просто, но создаёт много пустых запросов.

### Что такое long polling?

Клиент отправляет запрос, а сервер держит соединение открытым до появления
события или таймаута. После ответа клиент открывает новый запрос.

В short polling сервер отвечает сразу, а клиент регулярно повторяет запрос. В
long polling один запрос ждёт дольше и обычно создаёт меньше лишнего трафика.

### Когда использовать WebSocket или SSE?

Когда обновления приходят часто и серверу нужно саму отправлять их клиенту.
WebSocket поддерживает двусторонний обмен, SSE — поток событий от сервера к
клиенту. Для обычного CRUD этой работы они не нужны.

## OpenAPI и contract-first

### Что такое OpenAPI?

Это формальное описание HTTP API. В нём можно указать URL, методы, параметры,
JSON-модели, ограничения, ответы, ошибки и security-схемы.

По этому файлу можно строить документацию, генерировать код и проверять запросы.

### Что значит contract-first?

Сначала проектируется контракт, потом пишется реализация. В проекте сначала
меняется `marketplace.yaml`, затем `make generate` создаёт модели и интерфейс.

### Какие преимущества contract-first?

- клиент и сервер заранее согласуют формат;
- меньше расхождений между документацией и кодом;
- можно генерировать DTO и каркас сервера;
- frontend может начать работу до готового backend;
- ограничения проверяются одинаково;
- изменения API лучше видны в Git.

### Чем contract-first отличается от code-first?

В code-first сначала пишется код, а схема API строится из него. Например,
некоторые web-фреймворки автоматически генерируют OpenAPI по обработчикам.

Здесь источник истины — YAML, поэтому это contract-first.

### Зачем нужна кодогенерация?

Чтобы не переписывать вручную одни и те же поля в OpenAPI и Go. Если в контракте
появится новое обязательное поле, сгенерированный интерфейс или модель изменится,
и компилятор покажет места, которые надо поправить.

### Почему сгенерированный файл не хранится в Git?

Так написано в условии. Он воспроизводится командой `make generate` и создаётся
во время Docker build. В Git остаётся сам контракт и конфигурация генератора.

### Где используются сгенерированные модели?

Handler читает JSON прямо в `generated.ProductCreate`, `generated.OrderCreate`
и другие типы. Ответы тоже собираются в сгенерированные модели. Ручных HTTP DTO
нет.

### Зачем ещё нужен validation middleware?

Генератор создаёт типы и маршруты, но не обязан проверять все `minLength`,
`maximum`, `pattern` и `multipleOf`. Middleware читает OpenAPI и отклоняет
неправильный запрос до service.

### Почему валидация всё равно частично есть в service?

Контракт проверяет форму входа. Service проверяет бизнес-смысл, который нельзя
полностью описать OpenAPI: принадлежит ли товар продавцу, хватает ли остатка,
действует ли промокод, позже ли `valid_until`, чем `valid_from`.

## REST, gRPC и взаимодействие сервисов

### Чем REST отличается от gRPC?

REST обычно использует HTTP и JSON, его легко вызвать браузером или `curl`.
Контракт может быть OpenAPI.

gRPC обычно использует Protocol Buffers и HTTP/2. Клиент и сервер получают
строго типизированный сгенерированный код. Сообщения компактнее, есть streaming.

### Когда лучше REST?

- публичный API;
- браузерные и мобильные клиенты;
- простой CRUD;
- важна лёгкая ручная проверка;
- интеграция с разными внешними системами.

### Когда лучше gRPC?

- частые внутренние вызовы между сервисами;
- важен компактный бинарный формат;
- нужны строгие контракты и streaming;
- обе стороны контролируются одной командой или компанией.

### Почему REST может быть неудобен в high-load межсервисной системе?

Проблема не в том, что REST вообще не выдерживает нагрузку. Но типичная связка
JSON + много мелких синхронных запросов даёт больше трафика и затрат на
сериализацию. Каждый сервис ждёт ответ соседнего, а задержки складываются.

Для очень частых внутренних вызовов gRPC может быть эффективнее. Для событий,
где ответ прямо сейчас не нужен, лучше брокер сообщений.

### Какие проблемы бывают у синхронных вызовов?

- задержки нескольких сервисов складываются;
- сбой одного звена ломает всю цепочку;
- нужны таймауты и аккуратные retry;
- retry может повторить неидемпотентную операцию;
- возможны каскадные отказы;
- сложнее отладить длинную цепочку;
- сервисы сильнее зависят от контрактов и доступности друг друга.

### Почему синхронные вызовы повышают связанность?

Сервис A не просто знает контракт B. Он ещё зависит от того, что B прямо сейчас
доступен и отвечает достаточно быстро. Если B сам вызывает C, A косвенно зависит
и от C.

### Почему это приложение не разбито на микросервисы?

Заказ, остатки, промокод и операция пользователя должны изменяться одной
транзакцией. В одном приложении это обычная транзакция PostgreSQL. В
микросервисах пришлось бы добавлять сагу, сообщения и компенсации. Для этого
задания такая сложность не нужна.

## Go и структура проекта

### Почему Go?

На Go можно написать небольшой HTTP API без тяжёлого фреймворка. Есть удобная
стандартная библиотека, строгая типизация, простая сборка в один бинарник и
понятная работа с context.

### Почему `net/http`, а не Gin или Fiber?

Роуты всё равно генерируются из OpenAPI. Стандартной библиотеки достаточно, а
дополнительный framework добавил бы ещё один слой, который пришлось бы
объяснять.

### Что делают handler, service и store?

Handler занимается HTTP: читает request, вызывает service, пишет response.

Service содержит правила предметной области.

Store выполняет SQL и ничего не знает о JSON или HTTP-кодах.

### Почему не ORM?

Главные запросы здесь связаны с блокировками, транзакциями, частичным уникальным
индексом и точным порядком действий. С `pgx` SQL виден напрямую. Для такой работы
это проще показать и объяснить.

### Что такое `context.Context`?

Он переносит срок отмены и данные запроса по цепочке вызовов. В проекте через
context идут actor и request ID. Тот же context передаётся в pgx, поэтому запрос
к БД можно отменить, если HTTP-запрос закончился.

### Почему actor не передаётся глобальной переменной?

Глобальная переменная была бы общей для параллельных запросов. Context привязан
к одному запросу и безопасно идёт по его цепочке.

### Что такое graceful shutdown?

При SIGINT или SIGTERM сервер перестаёт принимать новые соединения и даёт
текущим запросам время закончиться. Это лучше, чем резко оборвать процесс во
время транзакции.

## PostgreSQL и транзакции

### Зачем Flyway?

Он хранит историю миграций и применяет их по порядку. Схема базы создаётся
одинаково на любом компьютере. Не нужно вручную копировать SQL в psql.

### Почему SQL-файлы считаются миграциями, если они ручные?

Запрещены SQL-файлы, которые человек сам запускает без инструмента. Здесь SQL
лежит в формате Flyway `V1__...`, а Flyway сам ведёт таблицу истории и применяет
их один раз.

### Зачем индекс на `products.status`?

Список товаров фильтруется по статусу. Индекс помогает PostgreSQL быстрее найти
нужные строки, особенно когда товаров много.

### Как заполняются `created_at` и `updated_at`?

`created_at` имеет `DEFAULT now()`. Для `updated_at` есть trigger, который перед
UPDATE ставит текущее время. Приложению не надо помнить об этом в каждом SQL.

### Что такое транзакция?

Группа операций, которая либо выполняется полностью, либо полностью
откатывается. Для заказа нельзя уменьшить stock и потом не сохранить сам заказ.

### Почему в коде есть `defer tx.Rollback()` даже при Commit?

Это страховка для любого раннего выхода. После успешного `Commit` вызов
`Rollback` уже ничего не меняет. Такой шаблон не даёт забыть откат в одной из
веток ошибки.

### Что делает `SELECT ... FOR UPDATE`?

Он читает строки и одновременно блокирует их для конкурирующего изменения до
конца транзакции. Поэтому два заказа не могут одновременно списать одну и ту же
последнюю единицу.

### Что произойдёт при двух заказах на последний товар?

Первая транзакция заблокирует товар. Вторая подождёт. После Commit первой вторая
прочитает новый stock, увидит ноль и вернёт `INSUFFICIENT_STOCK`.

### Почему товары блокируются по ID в одном порядке?

Если две транзакции берут несколько товаров в разном порядке, одна может держать
A и ждать B, а другая держать B и ждать A. Одинаковая сортировка снижает риск
такого deadlock.

### Зачем блокировать пользователя?

Чтобы два параллельных запроса одного пользователя не прошли одновременно
проверку частоты и наличия активного заказа.

### Зачем ещё частичный уникальный индекс активного заказа?

Блокировка — основная защита в коде. Индекс — дополнительный инвариант на уровне
БД. Даже если в будущем кто-то ошибётся в коде, база не позволит сохранить два
заказа `CREATED` или `PAYMENT_PENDING` одному пользователю.

### Почему цена сохраняется в `order_items`?

`products.price` — текущая цена. `price_at_order` — цена сделки. Изменение
каталога не должно менять историю старого заказа.

### Почему деньги хранятся в копейках в Go?

`float64` не может точно представить многие десятичные дроби. Внутри расчёта
`2499.90` хранится как `249990`. В PostgreSQL остаётся `NUMERIC(12,2)`.

### Почему soft delete, а не настоящий DELETE?

На товар могут ссылаться старые заказы. Статус `ARCHIVED` скрывает товар из
активных операций, но сохраняет историю и внешние ключи.

## Заказы и промокоды

### В каком порядке создаётся заказ?

1. Блокируется пользователь.
2. Проверяется частота.
3. Проверяется активный заказ.
4. Блокируются товары.
5. Проверяются существование, статус и stock.
6. Остатки уменьшаются.
7. Фиксируются цены.
8. Проверяется промокод.
9. Сохраняются заказ и позиции.
10. Записывается операция.
11. Выполняется Commit.

### Почему проверки идут до записи заказа?

Так код раньше возвращает понятную бизнес-ошибку и не создаёт временные строки,
которые потом надо чистить. При этом всё равно используется транзакция, потому
что состояние может меняться конкурентно.

### Что происходит при обновлении заказа?

Внутри одной транзакции старая бронь прибавляется обратно, затем проверяется и
вычитается новый набор. Старые позиции заменяются новыми, сумма и скидка
пересчитываются.

### Что если обновление не прошло?

Транзакция откатывается. Старые остатки и старые позиции остаются такими, какими
были до запроса.

### Что происходит при отмене?

Возвращается stock каждой позиции, `current_uses` промокода уменьшается, статус
становится `CANCELED`. Всё в одной транзакции.

### Почему промокод блокируется?

Без блокировки два заказа могли бы одновременно увидеть последнее доступное
использование и оба увеличить `current_uses`.

### Как считается процентная скидка?

Значение хранится с двумя знаками: `15.00%` внутри Go представляется как `1500`.
Скидка равна сумме заказа, умноженной на это значение и делённой на 10000.
Потом она ограничивается 70% суммы.

### Почему фиксированная скидка не делает отрицательную цену?

Используется минимум из размера скидки и суммы заказа. Итог не может быть меньше
нуля.

### Что будет, если после обновления сумма меньше минимальной для промокода?

Промокод снимается, `promo_code_id` становится `NULL`, скидка обнуляется, а
`current_uses` уменьшается.

### Где проверяются состояния заказа?

В `OrderService`. Обновлять позиции можно только в `CREATED`, отменять — в
`CREATED` и `PAYMENT_PENDING`. Административный endpoint разрешает только
следующий переход в цепочке.

### Почему статус нельзя перескочить?

Каждый статус означает завершённый этап. Если перейти из `PAYMENT_PENDING`
сразу в `SHIPPED`, система пропустит подтверждение оплаты.

## JWT и роли

### Что такое JWT?

Подписанный токен с claims. Сервер может проверить, что содержимое не изменено.
В проекте есть `sub` с ID пользователя, `role`, `token_type`, `exp` и `iss`.

### JWT шифрует данные?

Нет. Обычный JWT подписан, но payload можно прочитать. Поэтому туда нельзя класть
пароль или секретные данные.

### Зачем два токена?

Access token живёт недолго и отправляется в API. Refresh token живёт дольше и
используется только для получения новой пары. Если access token утечёт, время
риска ограничено.

### Почему refresh token нельзя использовать вместо access token?

В claim есть `token_type`. Middleware принимает только `access`, а endpoint
refresh — только `refresh`.

### Чем `401` отличается от `403`?

`401` — сервер не смог подтвердить личность: токена нет, он неверный или истёк.

`403` — пользователь подтверждён, но у него нет права на действие.

### Почему роль проверяется в service?

Только service знает данные ресурса. Middleware может проверить роль SELLER, но
не знает, принадлежит ли конкретный товар этому продавцу.

### Почему пароль хранится через bcrypt?

Пароль не должен лежать открытым текстом. Bcrypt хранит медленный односторонний
хэш с солью, поэтому его сложнее перебирать.

### Можно ли зарегистрировать ADMIN через API?

Нет. Публичная регистрация разрешает только USER и SELLER. Тестовый ADMIN
создаётся миграцией для защиты.

## Логирование

### Зачем request ID?

Он связывает ответ клиента и запись в логах. По этому значению можно найти конкретный запрос в логах.

### Почему request ID возвращается в заголовке?

Клиент может сохранить его вместе с ошибкой и сообщить разработчику, не передавая
весь лог.

### Что логируется?

Метод, шаблон endpoint, status, длительность, user ID, timestamp и request body
для изменяющих запросов.

### Почему нельзя логировать пароль и токены?

Логи часто доступны большему числу людей и хранятся долго. Утечка лога не должна
становиться утечкой учётных данных.

### Зачем `responseRecorder`?

Обычный `http.ResponseWriter` не сообщает middleware, какой код записал handler.
Обёртка запоминает `WriteHeader`, чтобы потом положить status в лог.

### Зачем recovery middleware?

Неожиданная panic не должна оборвать весь процесс. Middleware ловит её, пишет лог
и возвращает единый `500 INTERNAL_ERROR`.

## Docker

### Какие контейнеры запускаются?

- `postgres` — база;
- `flyway` — применяет миграции и завершается;
- `api` — Go-приложение.

### Почему API ждёт Flyway?

Приложение не должно стартовать на пустой схеме. Compose сначала ждёт healthy
PostgreSQL, затем успешное завершение Flyway и только потом запускает API.

### Зачем multi-stage Dockerfile?

В первом образе есть Go, генератор и компилятор. В финальный образ копируется
только бинарник и сертификаты. Итоговый контейнер меньше и не содержит инструменты
сборки.

### Что проверяет health-check?

`/health` не только отвечает HTTP, но и делает ping PostgreSQL. Поэтому `200`
означает, что API запущен и обязательная зависимость доступна.

### Что показать на защите?

```bash
docker compose up --build -d
docker compose ps
curl -i http://localhost:8080/health
bash scripts/demo.sh
make db
docker compose logs api --tail=30
docker compose down
```
