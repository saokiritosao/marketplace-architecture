# Почему проект сделан именно так

## Одно приложение, а не несколько сервисов

В прошлом задании была целевая микросервисная схема маркетплейса. Здесь задача
другая: нужно реально создавать заказ, менять остатки, применять промокод и
записывать операцию в одной транзакции.

Поэтому я оставил один API и одну PostgreSQL, но разделил код на модули. Это не
мешает позже вынести каталог или заказы в отдельный сервис, зато сейчас нет
распределённой транзакции и лишней инфраструктуры.

## Go без большого web-фреймворка

Для маршрутов используется стандартный `net/http`. Маршруты и типы всё равно
генерируются из OpenAPI, поэтому Gin или Fiber здесь почти ничего не упростили
бы. Чем меньше дополнительных слоёв, тем легче объяснить запрос от HTTP до SQL.

## Contract-first

Сначала меняется `api/openapi/marketplace.yaml`, потом запускается
`make generate`. Код обработчиков реализует сгенерированный интерфейс, а JSON
читается в сгенерированные модели. Отдельных ручных HTTP DTO в проекте нет.

## SQL написан явно

ORM мог бы сократить несколько простых запросов, но в заказах всё равно нужны
`FOR UPDATE`, частичные индексы и точный порядок действий. С `pgx` эти места не
спрятаны и нормально читаются на защите.

## Деньги в копейках

Внутри Go используется `money.Cents`, то есть `int64`. В базе остаётся
`NUMERIC(12,2)`, как требует схема. На границе API число переводится в копейки,
а перед ответом обратно в число.

## Блокировка пользователя и товаров

Сначала блокируется строка пользователя. Так две операции одного пользователя
не пройдут проверку лимита одновременно и не создадут два активных заказа.
Потом товары блокируются в порядке ID. Одинаковый порядок уменьшает вероятность
взаимной блокировки транзакций.

## Ограничение скидки

Фраза про процентную скидку в задании сформулирована неоднозначно. В проекте
зафиксировано простое правило: процентная скидка не может уменьшить сумму больше
чем на 70%. Фиксированная скидка не может сделать итог отрицательным.

## Дополнительный endpoint статуса

`PUT /orders/{id}/status` добавлен для ADMIN, чтобы на защите можно было реально
показать цепочку `CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED` и
ошибку при попытке перескочить через состояние. Отмена всё равно выполняется
через отдельный `/cancel`, потому что она возвращает остатки и использование
промокода.
